# Durability Guarantees

What NopalDB guarantees when the process dies at an arbitrary point (e.g. `SIGKILL`, power loss at the OS-buffer level notwithstanding), and what it does not. Continuously exercised by the SIGKILL crash harnesses (`nopaldb/tests/crash_commit_test.rs`, `crash_mixed_load_test.rs`) run on every CI build and nightly with 100 kill rounds.

## Committed transactions

A `Transaction::commit()` that **returned `Ok`** is durable:

1. The whole write-set (Begin + operations + Commit) is written to the WAL **before any storage mutation**, with one fsync per commit *group*: concurrent commits queued at the single-writer applier share a single fsync (group commit), and no write-set in a group is applied until the group's records are durable. If the fsync did not complete, `commit()` never returned.
2. Storage application happens after WAL durability. If the process dies mid-application, the next `Graph::open()` **replays** the committed operations from the WAL (redo), rebuilding MVCC version chains with their original commit timestamps.
3. The per-node version write-set (previous-version invalidation, new version, current pointer, version lists, current record) applies as a **single atomic storage batch** — a crash cannot leave a node without a current version.

A commit whose `Ok` was never observed may or may not be durable (standard "committed but unacknowledged" semantics): if its Commit record reached the WAL, it will be replayed; otherwise it is discarded.

## Torn WAL tails

A crash mid-append can leave a torn record at the WAL tail (incomplete length prefix, truncated payload, or undecodable bytes). On open, the log is scanned tolerantly and **truncated to the last valid record**. A torn record was never acknowledged, so discarding it is safe. Databases never become unopenable due to a torn tail.

## Derived structures

Adjacency lists and property indexes are persisted incrementally by the single-writer apply funnel, and are **not** journaled in the WAL. After a crash recovery (WAL replay ran), adjacency is **rebuilt from the edges** — the source of truth — instead of trusting possibly-stale snapshots. Structural invariants (no orphaned edges, bidirectional adjacency consistency, no duplicates, index↔data consistency) are asserted by the crash harnesses on every reopen.

## Logical clocks

MVCC timestamps and transaction ids are persisted as monotonic bounds and restored on open (falling back to the WAL maxima and a version scan for older databases). Time-travel ordering (`history()`, `as_of()`) is preserved across restarts and crashes.

## Direct (non-transactional) writes

Since 0.5.23, `graph.add_node()`, `add_edge()`, `delete_node()` and `delete_edge()` are **journaled too**: the single-writer applier records each one as an automatic transaction (`Begin` + operation + `Commit`) in the same WAL batch as the transactional commits it is draining, *before* applying it, and WAL replay on open redoes them. What changes is *when* that record reaches the disk, chosen with `StorageOptions::direct_write_durability`:

| mode | what happens on `add_node` | survives process death (`SIGKILL`, panic, OOM kill) | survives power loss / kernel panic | cost per direct write |
|---|---|---|---|---|
| `ProcessCrash` (default) | the WAL batch is written without `fsync`; a background syncer fsyncs every `flush_every_ms` of the profile (500–3000 ms) and `close()` fsyncs | **yes** — the OS keeps what the process wrote | up to the last sync interval may be lost | microseconds (serialize + one `write`) |
| `Immediate` | the WAL batch is fsynced, like a transaction commit | yes | yes | one fsync per applier batch (milliseconds for an isolated write) |

Transactions always fsync per applier batch regardless of this option. A batch that mixes direct writes and commits is fsynced as a whole.

Before 0.5.23 direct writes did not touch the WAL at all: an acknowledged direct write less than one flush interval before a crash was lost, and with redb even data already in the OS cache was discarded (non-durable commits are rolled back on reopen). The crash harness now asserts, on every reopen, that every direct write acknowledged before the kill is present (and every acknowledged delete is gone).

Platform note (macOS/APFS): a plain `write()` to the WAL waits for any `F_FULLFSYNC` in flight on the same volume. sled fsyncs its own log on every buffer write outside Linux, so with sled the default mode costs ~4 ms per direct write on a Mac (redb: ~40 µs; measured on the same machine, and reproduced with redb plus an artificial fsync storm). On Linux sled uses `sync_file_range` and the two do not interfere.

Two details of the redo:

- Replay goes through the same apply funnel, so a directly-created node recovered from the WAL gets a first MVCC version stamped with its logical timestamp (the same reconstruction used for committed nodes).
- Writes generated by the replay itself are not journaled again.

## WAL checkpoints and truncation

The WAL is the redo log: everything in it is replayed on the next `open`, so it must not grow without bound. Since 0.6.4 (#150) it is truncated by a **checkpoint**, and a checkpoint happens in three situations:

| trigger | when |
|---|---|
| automatic | the single-writer applier finishes a batch and the WAL is at or past `StorageOptions::wal_checkpoint_bytes` (default 16 MiB, `0` disables the automatic one) |
| `close()` | always, on a writable graph; the next open replays nothing |
| `Graph::checkpoint()` / `graph.checkpoint()` | on demand, e.g. right after a large load so the next open is instant |

What a checkpoint does, in this order and under the write gate (so no batch is between "written to the WAL" and "applied to the engine" while it runs): persist the logical clocks, ask the engine for a **durable** checkpoint (redb: commit the write window with `Durability::Immediate`; sled: `flush`), then empty the WAL and leave a single fsynced `Checkpoint` record. The rule that never bends: **a WAL record is dropped only after the engine has made its effect durable.** Before 0.6.4 `checkpoint()` truncated without the engine flush, so a power loss right after a checkpoint could lose committed writes; and nothing called it in production anyway, so the WAL grew without limit.

Two consequences worth knowing:

- A checkpoint costs one engine fsync (milliseconds). At the default threshold that is one fsync per ~64k operations; lowering the threshold is cheap, raising it only lengthens the replay after a crash.
- In the default `ProcessCrash` mode for direct writes, a checkpoint is also the moment their WAL records become power-loss safe (the engine has them, durably). Between checkpoints the periodic syncer still bounds the exposure to `flush_every_ms`.

The SIGKILL harness runs the child with a 32 KiB threshold, so kills land right after truncations many times per round, and asserts on every reopen that everything acknowledged before the kill is present.

`graph.get_stats()["wal_bytes"]` (Python) and `Graph::wal_bytes()` (Rust) report the current size: what the next open would replay if the process died now.

## From Python

The same guarantees, by call:

| call | durable when it returns | survives power loss | recover after an interrupted load |
|---|---|---|---|
| `graph.begin_transaction()` … `tx.commit()` | yes: the whole write-set is fsynced in the WAL before `commit()` returns | yes | reopen: committed transactions are replayed |
| `graph.upsert(...)`, `graph.upsert_many(...)` | yes: each upsert (each chunk of 1 024 for `upsert_many`) is a transaction | yes | reopen; re-running the same upserts is a no-op for what already landed |
| `graph.add_node(...)`, `add_edge`, `delete_node`, `delete_edge` (direct writes) | to process death, immediately; to power loss after the next syncer tick (`flush_every_ms`), `checkpoint()` or `close()` | up to the last sync interval may be lost | reopen: acknowledged direct writes are replayed |
| `graph.bulk_loader(...)` … `loader.finish()` | when `finish()` returns: it ends with a durable engine checkpoint | yes, once `finish()` returned; a load killed before `finish()` keeps the batches the engine already made durable and loses the rest (bulk batches do not go through the WAL) | rerun the load; the bulk path is not idempotent by key, so start from an empty directory or use `upsert_many` for reruns |
| `graph.checkpoint()` | n/a | makes everything above power-loss safe and empties the WAL | shortens the next open |
| `graph.close()` | n/a | same as `checkpoint()`, then releases the directory | a database not closed is reopened by `Graph.open()` with automatic replay; no manual step |

Recovering an interrupted load is always the same action: `Graph.open()` the directory again. Replay runs before `open` returns, torn WAL tails are discarded, adjacency is rebuilt from the edges, and the indexes are rebuilt from their catalog. Nothing acknowledged as durable above is lost; nothing needs to be repaired by hand.

## Scope

- Durability is at the `fsync` level; disks or VMs that lie about `fsync` weaken every layer equally.
- Creating a **new** database is a one-time cost dominated by fsyncs: with redb about 60 ms on a Mac (the engine fsyncs when it creates the file and again when the handle is dropped), with sled about 20 ms. It is paid once per database directory, never per write; the `bulk_load/1k_nodes_fresh_db` bench includes it on purpose and `bulk_load/1k_nodes_open_db` excludes it.
- The storage engine's own commits are not the durability boundary: NopalDB applies them without fsync (redb batches several operations into one commit window of a few milliseconds; sled buffers in its page cache) and relies on the WAL plus the engine checkpoint. The WAL is what survives until a checkpoint makes the engine state durable, and only then is it truncated.
- One process per data directory (see the Operational Model in the README); the on-disk state is only defined when the owning process is the single writer.
